# 页面模块结构拆解分析

## 文档目的

本文档用于分析 `bot-frontend` 当前的页面模块结构，并明确后续页面层面的治理规则与修改方向。

本文档的核心目标是回答以下问题：

- 当前哪些目录承载真实业务
- 哪些目录是模板、演示、公共页面或历史遗留
- 后续页面应该往哪里放
- 页面、模块、接口、路由之间应该如何保持一致

本文档应与以下文档一起使用：

- [项目整体重构规则与修改方向总览.md](./项目整体重构规则与修改方向总览.md)
- [公共组件与页面逻辑优化三大方向分析.md](./公共组件与页面逻辑优化三大方向分析.md)
- [路由与权限体系拆解分析.md](./路由与权限体系拆解分析.md)
- [请求与接口体系拆解分析.md](./请求与接口体系拆解分析.md)

## 一、当前页面目录结构概览

当前项目的页面相关目录主要包括：

- `src/views`
- `src/operation`
- `src/management`

其中：

- `src/operation` 主要承载运营端真实业务页面
- `src/management` 主要承载代理端真实业务页面
- `src/views` 当前同时承载：
  - 基础公共页面
  - 登录/错误页
  - 演示与示例页
  - 一部分历史保留页面

从目录职责角度看，这三层并不是完全平级的。

当前更合理的理解是：

- `src/operation` 和 `src/management` 是“业务系统层”
- `src/views` 更接近“基础页面层 + 演示遗留层”

这是当前结构里最重要的优点之一。

项目没有把运营端和代理端业务页面长期混放在 `src/views`，而是已经开始迁移到：

- `src/operation`
- `src/management`

这为后续治理提供了非常好的基础。

### 2. 运营端目录结构已经较接近主路由结构

这意味着运营端已经具备“路由名 = 页面模块名 = 权限归属”的雏形，是后续最值得继续强化的一套结构。

### 3. 代理端目录结构也已经建立骨架

[src/management/README.md](/abs/path/C:/Users/Administrator/Desktop/ChaoNeng/bot-frontend/src/management/README.md)

虽然还存在历史迁移痕迹，但方向是明确的。

### 4. 页面专属组件下沉意识已经存在

- `constants.ts`

- `composables/`

这说明项目已经开始从“大页面全写在一个文件里”往“页面模块内部自组织”演进。

## 三、当前存在的核心问题

## 3.1 `src/views` 当前职责过重且混杂

`src/views` 现在同时包含：

- 登录页
- 404/403/500
- Personal
- Redirect
- Dashboard
- Components 演示页
- Example 示例页
- Function 功能演示页
- Guide
- hooks 演示页
- Level 菜单演示页
- 部分旧管理页面和旧权限页面

这带来的问题是：

- `views` 既像基础页面目录，又像 demo 目录，又像遗留业务目录
- 新人接手时很难快速判断：
  - 哪些还能继续加
  - 哪些只是演示
  - 哪些是待迁移历史内容

如果不进一步定规则，`views` 未来会继续成为“什么都能放一点”的目录。

## 3.2 页面目录分层规则已经有方向，但还没有成为硬约束

当前虽然有：

- `operation/README.md`
- `management/README.md`

但从整体项目状态看，这还更多是“推荐结构”，还没有完全变成所有人必须遵守的硬约束。

结果是：

- 新增页面时仍然存在落到 `views` 的可能
- 跨模块复用时容易直接从某业务模块 import 页面专属实现
- 页面与 API、路由、权限的同构关系还不够彻底

## 3.3 页面级共享能力存在“业务模块公共层”和“项目公共层”边界模糊

例如当前存在：

- `src/operation/components`
- `src/operation/utils`
- `src/components`
- `src/hooks`

这说明项目已经有两种共享层：

1. 全项目共享层
2. 运营端模块共享层

问题在于：

- 什么能力应该进入 `src/components`
- 什么能力应该留在 `src/operation/components`
- 什么能力只是单页专属，不该上升为共享层

这部分如果不先定规则，后面会出现：

- 共享层持续膨胀
- 业务耦合向公共层反向渗透
- 组件表面通用，实际带着业务假设

## 3.4 页面与路由、API、权限的同构关系还不够彻底

当前项目已经开始推动：

- 路由主路由名
- 页面目录
- API 目录
- 权限名

相互对应。

但整体还没有完全收敛，比如：

- 一部分页面仍保留在 `src/views`
- 一部分旧页面逻辑还未彻底迁走
- 同一业务主路由下的公共能力，有时在页面目录中，有时在模块公共目录中

这意味着结构方向是对的，但仍在迁移中。

## 3.5 模板页、示例页、真实业务页尚未彻底隔离

当前 `src/views/Components`、`src/views/Example`、`src/views/Function`、`src/views/hooks` 等目录主要用于：

- 组件演示
- 模板示例
- 开发验证

这些目录存在是合理的，但问题是没有和真实业务页形成足够强的认知隔离。

后续如果不明确：

- 哪些目录禁止承接真实业务
- 哪些目录只保留演示用途

结构会继续混杂。

## 3.6 模块内公共资源与页面专属资源的边界需要更细

当前很多页面已经开始有：

- `components/`
- `constants.ts`
- `utils.ts`
- `types.ts`

这是好现象，但仍需要明确：

- 页面专属的工具函数放页面目录内
- 主路由内多个页面共用的放主路由公共层
- 跨主路由共用的再上升到全局公共层

否则模块内部仍然容易出现“顺手就上提到共享目录”的情况。

## 四、后续统一规则

## 4.1 页面目录总规则

### 规则一：真实业务页面只能进入系统业务目录

后续真实业务页面统一要求：

- 运营端页面进入 `src/operation`
- 代理端页面进入 `src/management`

原则上不再把新增真实业务页面放入 `src/views`。

### 规则二：`src/views` 仅保留基础页面、通用页面、演示页和遗留迁移页

后续 `src/views` 的角色应明确为：

- 登录相关
- 错误页
- Redirect
- Personal
- 组件/功能/示例演示
- 暂未迁移完成的历史页面

并且要明确：

- `src/views` 不是新业务页面默认落点

### 规则三：页面结构必须尽量与路由主路由保持同构

后续要求：

- 主路由名应尽量对应一级目录
- 页面名应尽量对应二级目录
- 页面入口统一 `index.vue`

例如：

- `OperationCenter/RechargeOrder/index.vue`
- `UserGroup/MessageList/index.vue`

这能极大降低定位成本。

---

## 4.2 页面模块内部规则

### 规则一：页面专属资源优先就近放置

若某资源只服务一个页面，应优先放在页面目录中，例如：

- `components/`
- `constants.ts`
- `types.ts`
- `utils.ts`
- `composables/`

不要一开始就上提到主路由共享层或项目公共层。

### 规则二：主路由内部复用资源放主路由公共层

如果多个同主路由页面复用，才允许上提到：

- `src/operation/<MainRoute>/components`
- `src/operation/<MainRoute>/utils`
- `src/operation/<MainRoute>/composables`

代理端同理：

- `src/management/<MainRoute>/components`
- `src/management/<MainRoute>/utils`
- `src/management/<MainRoute>/composables`

### 规则三：跨主路由复用能力再上升到全局公共层

只有真正跨多个业务主路由复用的能力，才考虑进入：

- `src/components`
- `src/hooks`
- `src/utils`

后续应避免把带明显业务语义的组件或工具直接提升到全局层。

---

## 4.3 页面与路由/API/权限的同构规则

### 规则一：页面目录、路由归属、API 目录尽量保持一致

后续目标是形成稳定映射：

- 页面在 `src/operation/<MainRoute>/<PageName>`
- API 在 `src/api/opertion/<MainRoute>/<PageName>`
- 路由在 `src/router/modules/operation.ts`
- 权限名尽量和路由 `name` 对应

代理端同理。

### 规则二：权限命名与页面目录不要长期脱节

页面目录和权限命名不要求完全字符串一致，但必须保持稳定映射关系。

避免出现：

- 目录名、页面名、权限名差别过大
- 维护者无法直观从目录推断权限归属

### 规则三：页面迁移必须成组迁移

后续页面迁移不应只迁页面文件本身，还应一并检查：

- 路由引用
- API 引用
- 权限归属
- 页面内部相对路径
- 模块内公共依赖

不能只迁页面路径，不处理依赖关系。

---

## 4.4 演示与遗留页面规则

### 规则一：演示页与业务页必须概念隔离

后续应明确：

- `views/Components`
- `views/Example`
- `views/Function`
- `views/hooks`

这些目录主要用于：

- 组件能力展示
- 开发验证
- 模板示例

不作为真实业务功能的长期承载目录。

### 规则二：遗留页允许保留，但必须明确迁移状态

对仍然留在 `src/views` 的旧业务页面，后续应逐步补充状态说明：

- 是否仍在使用
- 是否待迁移
- 是否仅作兼容保留

避免出现“文件还在，但没人知道它是不是还活着”的情况。

### 规则三：清理应在引用完全切走后再做

迁移完成前，不建议直接删除旧页面目录。

应遵循：

1. 新目录可运行
2. 路由已切换
3. API 已对齐
4. 搜索引用确认旧路径已空
5. 再删除旧目录

---

## 4.5 模块公共层规则

### 规则一：模块级共享目录只能服务本模块

例如：

- `src/operation/components`
- `src/operation/utils`

这类目录的能力应默认理解为：

- 只服务运营端
- 不保证代理端适用
- 不作为项目级通用能力默认来源

### 规则二：业务共享组件不能伪装成全局通用组件

后续如果组件高度依赖某个业务模型，例如消息、按钮配置、机器人配置等，应留在业务模块层，不宜直接上提到 `src/components`。

### 规则三：模块级公共层也要避免持续膨胀

若某个模块公共目录不断变大，后续应进一步区分：

- 当前主路由公共层
- 页面专属层
- 更细粒度功能目录

避免模块公共层再次变成“大杂烩”。

## 五、建议处理的小点

## 5.1 `src/views` 的职责收口

- 明确哪些目录属于基础页
- 明确哪些目录属于演示页
- 标记哪些目录属于历史迁移保留
- 后续禁止新增真实业务页到 `src/views`

## 5.2 `src/operation` 与 `src/management` 的结构固化

- 强化“主路由 = 一级目录”
- 强化“页面 = 二级目录”
- 强化“页面入口 = index.vue”
- 强化“页面目录内自带 components/constants/types/utils/composables”

## 5.3 页面迁移规则标准化

- 页面迁移时同步迁 API
- 页面迁移时同步迁路由引用
- 页面迁移时同步清理旧 import
- 页面迁移时同步核对权限映射

## 5.4 模块共享层边界整理

- 识别哪些属于页面专属能力
- 识别哪些属于主路由共享能力
- 识别哪些属于真正项目级通用能力
- 减少错误上提和错误复用

## 5.5 演示页治理

- 确认 `views/Components`、`views/Example` 等是否继续保留
- 若保留，明确它们的用途边界
- 若不再需要，后续另做清理计划

---

## 六、建议推进顺序

### 第一阶段：先统一目录规则

优先完成：

- `views / operation / management` 职责说明
- 真实业务页落点规则
- 页面目录规范说明

### 第二阶段：收口遗留与共享边界

优先处理：

- `views` 中历史业务页识别
- 模块级共享目录边界明确
- 页面专属资源归位

### 第三阶段：逐步推进迁移与清理

优先处理：

- 页面与 API 同构迁移
- 旧引用清理
- 旧目录清理

---

## 七、当前阶段结论

当前项目的页面结构已经走在正确的方向上：

- 真实业务开始从 `src/views` 迁出
- 双系统目录已经建立
- 路由与页面结构正在逐步同构

但目前仍处于“迁移中间态”，主要问题不是结构完全错误，而是：

- `views` 仍然职责混杂
- 页面落点规则还没彻底变成硬约束
- 模块共享层边界还不够细
- 页面、路由、API、权限的同构关系还没有完全收口

因此这一块后续最合适的策略是：

- 先把目录规则定死
- 再把遗留结构逐步迁清
- 最后把共享边界和页面组织方式稳定下来

只要页面模块结构定稳，后续公共组件治理、接口治理、权限治理都会更容易落地。
