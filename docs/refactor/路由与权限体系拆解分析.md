# 路由与权限体系拆解分析

## 文档目的

本文档用于分析 `bot-frontend` 当前的路由与权限体系，并为后续修改提供统一规则与方向。

本文档重点解决的问题不是“当前能不能跑”，而是：

- 当前路由体系是否清晰
- 权限控制是否收口
- 双系统结构是否足够稳定
- 后续要怎么改，才能在不破坏现有业务的前提下逐步变得更稳

本文档应与以下文档配合使用：

- [项目整体重构规则与修改方向总览.md](./项目整体重构规则与修改方向总览.md)
- [公共组件与页面逻辑优化三大方向分析.md](./公共组件与页面逻辑优化三大方向分析.md)

## 一、当前体系概览

当前项目的路由与权限体系由以下几部分共同构成：

- 路由入口：

- 路由模块：

  - [src/router/modules/management.ts](/abs/path/C:/Users/Administrator/Desktop/ChaoNeng/bot-frontend/src/router/modules/management.ts)
  - [src/router/modules/operation.ts](/abs/path/C:/Users/Administrator/Desktop/ChaoNeng/bot-frontend/src/router/modules/operation.ts)
- 权限守卫：
  - [src/permission.ts](/abs/path/C:/Users/Administrator/Desktop/ChaoNeng/bot-frontend/src/permission.ts)
- 权限 store：
  - [src/store/modules/permission.ts](/abs/path/C:/Users/Administrator/Desktop/ChaoNeng/bot-frontend/src/store/modules/permission.ts)
- 路由辅助工具：
  - [src/utils/routerHelper.ts](/abs/path/C:/Users/Administrator/Desktop/ChaoNeng/bot-frontend/src/utils/routerHelper.ts)
- 路由类型定义：
  - [types/router.d.ts](/abs/path/C:/Users/Administrator/Desktop/ChaoNeng/bot-frontend/types/router.d.ts)

从整体结构来看，当前体系已经形成了比较明确的主干：

1. 通过 `VITE_SYSTEM_TYPE` 区分 `Management` 与 `Operation`
2. 基础公共路由单独维护
3. 系统专属路由按模块拆分
4. 登录后通过权限 store 生成并注入动态路由
5. 页面级按钮权限依赖 `route.name` 和 `meta.buttonList`

这套结构本身是可工作的，也具备继续演进的基础。但随着业务膨胀，已经出现一些需要明确收口的地方。

## 二、当前体系中的主要优点

### 1. 双系统已经做了物理分层

这是当前体系里非常重要的优点。

项目没有把所有路由混在一个总文件里，而是分成：

- 公共 `base`
- 管理端 `management`
- 运营端 `operation`

这为后续治理提供了很好的基础，因为双系统边界已经存在，不需要从零重建。

### 2. 权限注入集中在权限层处理

无论最终走：

- 静态路由
- 前端权限控制动态路由
- 服务端动态路由

当前都统一汇总到权限 store 和路由守卫中处理，而不是页面各自决定能不能访问。这是正确方向。

### 3. 页面权限与按钮权限已经初步统一到路由语义

运营端当前权限模型的关键特点是：

- 页面菜单权限与 `route.name` 强关联
- 按钮权限通过 `${route.name}.action` 形式衍生
- `meta.buttonList` 提供按钮能力描述

这种模型虽然还有一些细节需要规范，但方向上是统一的，比散落写死判断要好很多。

### 4. 路由辅助工具比较完整

`routerHelper.ts` 中已经有：

- 前端路由生成
- 服务端路由生成
- 多级路由拍平
- redirect 归一化
- 路径解析

说明当前体系已经不仅仅是“配置路由”，而是具备一定程度的平台化思路。

## 三、当前存在的核心问题

## 3.1 路由定义层存在职责混叠

当前问题主要体现在：

- `operation.ts` 中直接依赖 `VITE_SYSTEM_TYPE` 决定是否导出路由
- `index.ts` 中也在根据 `VITE_SYSTEM_TYPE` 进行最终路由拼装
- `permission.ts` 和 `permission store` 中又再次根据系统类型决定如何生成动态路由

这会导致一个问题：

系统切换逻辑分散在多个层级中，而不是由一个中心规则统一控制。

这类问题短期内不一定出 bug，但长期会带来：

- 新增路由时不确定该加在哪一层判断
- 排查某条路由为什么没生效时成本更高
- 双系统差异逻辑更容易继续分散

## 3.2 路由生成模式过多，但边界还不够稳定

当前存在三种模式：

- `static`
- `frontEnd`
- `server`

且由以下状态组合控制：

- `appStore.getDynamicRouter`
- `appStore.serverDynamicRouter`

问题不在于模式多，而在于“规则表达不够显式”。

当前不够清晰的地方包括：

- 在实际生产中，哪种模式才是主模式
- `Management` 和 `Operation` 是否都应该支持完整三种模式
- 服务端动态路由是否真的是长期需要保留的核心能力
- 前端权限过滤和服务端返回的角色路由之间，谁是主数据源

如果这些边界不先定，后续越改越容易把逻辑继续摊平在多个文件里。

## 3.3 权限规则仍然分散在多个位置

当前权限相关逻辑散布在：

- 路由守卫
- `permission store`
- `operation/utils/permission.ts`
- `directives/utils/hasPermi.ts`
- 各页面内部判断
- 角色管理页面权限树构造逻辑

这说明“权限体系已经存在，但还没有完全收口”。

风险在于：

- 同一权限语义可能在不同地方用不同方式解释
- 菜单权限、页面权限、按钮权限的规则虽然有关联，但还不是完全单源
- 后续新增权限动作时容易出现不一致

## 3.4 路由 `meta` 的约束还不够统一

在 [types/router.d.ts](/abs/path/C:/Users/Administrator/Desktop/ChaoNeng/bot-frontend/types/router.d.ts) 中，当前 `RouteMetaCustom` 定义了不少字段，但代码里实际使用的还有一些约定并没有完整体现在类型中，比如：

- `buttonList`
- `followRoute`

问题在于：

- 类型层没有完整表达真实约定
- 后续维护者会更依赖“经验”而不是“类型提示”
- 新增 meta 字段时更容易失控

## 3.5 守卫层承担职责偏多

`src/permission.ts` 当前除了做访问控制，还承担了：

- token 双重过期校验
- 本地存储校验
- 动态注入路由
- 路由缺失兜底
- 登录态重定向

这些功能本身都合理，但过于集中在一个守卫文件里，会带来两个问题：

- 修改风险高
- 后续继续叠加业务条件的诱惑很大

这类文件后期最容易演变成“全局流程杂糅入口”。

## 3.6 路由黑名单和临时过滤逻辑存在“规则外硬编码”

在权限 store 中当前存在：

- `routeBlacklist = ['BotPrice']`
- 对 `Management` 下 `/data_statistics` 的过滤

这类逻辑本质上说明：

- 当前路由主配置与实际可用路由之间还有差距
- 系统中存在一些“临时兼容规则”

如果不进一步收口，这类规则会逐步增加，最后变成难维护的“隐藏业务逻辑”。

## 四、后续统一规则

## 4.1 路由结构规则

### 规则一：系统差异只在路由入口层和权限层决定

后续约束：

- `base / management / operation` 模块只负责声明自己的路由结构
- 不在模块文件内部继续写系统判断
- 系统切换逻辑统一收口到：
  - 路由入口
  - 权限生成层

这意味着后续应逐步减少类似 `operation.ts` 内部根据环境变量决定是否返回空数组的模式。

### 规则二：路由模块文件只描述路由，不附带运行时流程逻辑

路由模块中允许定义：

- path
- name
- component
- redirect
- meta
- children

不建议继续增加：

- 权限流程判断
- 环境分支流程
- 临时行为开关

### 规则三：所有隐藏/跟随/按钮能力必须在 `meta` 类型中显式声明

后续要求：

- 路由 `meta` 的所有项目级约定，都必须写进类型定义
- 不允许只在业务里“默认约定存在某字段”

建议补齐的字段包括：

- `buttonList`
- `followRoute`
- 必要时为 `permissionMode`、`menuGroup` 等未来字段预留规范

---

## 4.2 权限规则

### 规则一：页面权限、菜单权限、按钮权限必须同源

后续统一采用以下方向：

- 菜单权限基于 `route.name`
- 页面访问权限基于路由过滤结果
- 按钮权限基于 `${route.name}.${action}`
- `meta.buttonList` 只描述页面支持哪些动作，不直接代表用户拥有这些动作

也就是说：

- `buttonList` 是页面能力定义
- `userInfo.permissions` 是用户授权结果
- 两者结合后才得出是否可见/可用

### 规则二：权限判断必须收口到工具层或指令层

后续目标：

- 页面尽量不要自己拼权限字符串
- 页面尽量不直接写权限集合判断逻辑

建议统一使用：

- 指令
- 统一的权限判断工具
- 模块内少量组合式封装

### 规则三：超管逻辑必须作为统一特例，而不是各处散判

当前已有 `*` 作为超管标识。

后续要求：

- 超管规则只保留一套统一解释
- 页面不再各自散写 `permissions.includes('*')`
- 所有超管分支尽量通过公共判断函数完成

---

## 4.3 动态路由规则

### 规则一：先明确主模式，再保留兼容模式

当前三种模式并存没有问题，但后续必须明确：

- 默认主模式是什么
- 哪些模式是保留兼容
- 哪些模式只作为开发期或特殊场景存在

建议方向：

- `Operation` 端优先以“前端定义路由 + 权限过滤”为主
- `serverDynamicRouter` 若不是核心生产依赖，应弱化为兼容能力
- `static` 作为最简单兜底模式保留

### 规则二：服务端动态路由必须有更严格的校验边界

如果继续保留服务端动态路由，后续规则应包括：

- 返回组件路径必须可验证
- 不存在的组件必须有可观测降级策略
- 不允许 silently skip 后完全无提示

### 规则三：路由注入过程必须尽量幂等

后续要求：

- 路由生成只做一次主注入
- 重新登录、登出、切换用户时要有明确重置策略
- 避免重复注入、重复过滤、重复拍平

---

## 4.4 路由守卫规则

### 规则一：守卫只做访问控制主流程

后续守卫应尽量只保留：

- 登录态判断
- token 是否有效
- 路由是否已生成
- 当前目标是否允许进入
- 不允许时跳去哪

不建议继续往守卫中叠加更多业务细节。

### 规则二：登录态校验与 token 校验逻辑应模块化

当前 token 过期判断写在守卫中，且夹杂 localStorage 二次校验。

后续建议：

- 抽出独立的会话校验方法
- 守卫只调用结果，不展开实现细节

### 规则三：404 与缺失路由策略必须统一

后续要求：

- 404 路由只保留一套稳定注入策略
- 路由不存在的判断逻辑统一处理
- 避免既有静态 404，又有运行时动态兜底，但行为不一致

## 五、建议处理的小点

## 5.1 路由配置层

- 清理路由模块内的系统判断逻辑
- 明确 `base / management / operation` 的边界
- 补齐 `meta` 类型定义
- 收口临时过滤与黑名单逻辑

## 5.2 权限生成层

- 梳理 `static / frontEnd / server` 三种模式的真实使用场景
- 明确主模式与兼容模式
- 收口 `generateRoutes` 中的系统差异判断
- 让权限过滤规则更可解释

## 5.3 守卫层

- 抽离 token 校验逻辑
- 抽离登录态判断辅助方法
- 收口 404/不存在路由兜底逻辑
- 降低守卫文件复杂度

## 5.4 页面与按钮权限层

- 统一按钮权限判断入口
- 避免页面自己拼 `${routeName}.xxx`
- 规范 `buttonList` 的定义与使用边界
- 让角色权限编辑页与实际运行时权限模型完全同源

## 5.5 类型与约束层

- 完善 `types/router.d.ts`
- 给项目级 `meta` 约定做统一说明
- 必要时增加路由配置 lint / 校验脚本

---

## 六、建议推进顺序

为了稳妥推进，建议按以下顺序处理：

### 第一阶段：先统一规则，不动大结构

先完成：

- 路由 meta 约定整理
- 权限命名规范整理
- 动态路由模式边界整理

这一阶段重点是“统一认知”。

### 第二阶段：收口分散逻辑

重点处理：

- 守卫职责拆分
- 权限判断工具统一
- 路由黑名单和临时过滤逻辑清理

这一阶段重点是“减少分散判断”。

### 第三阶段：优化结构稳定性

重点处理：

- 路由配置文件边界优化
- 动态路由主模式确认
- 页面权限与按钮权限同源化

这一阶段重点是“让体系稳定下来”。

---

## 七、当前阶段结论

当前项目的路由与权限体系并不是混乱到需要重写，反而已经具备不错的基础分层。但它已经进入了一个很典型的阶段：

- 基础结构是对的
- 历史兼容和临时逻辑开始增多
- 权限判断逐步分散
- 类型约束还没有完全跟上真实约定

因此这部分最合适的策略不是“推倒重来”，而是：

- 先统一规则
- 再收口逻辑
- 最后逐步做结构优化

如果继续按当前方式自然扩展，后面路由与权限体系会越来越依赖经验维护；如果现在开始规则化治理，后续整个项目会稳很多。
