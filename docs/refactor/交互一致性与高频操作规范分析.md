# 交互一致性与高频操作规范分析

## 文档目的

本文档用于分析 `bot-frontend` 当前在高频交互场景中的使用体验与实现方式，并为后续统一交互规则提供依据。

这里说的“交互一致性”，不是单纯视觉样式一致，而是指用户在不同页面中执行高频动作时，是否能获得稳定、可预期、低打断的体验。

本文档重点关注以下高频场景：

- 搜索
- 重置
- 导出
- 列表刷新
- 行内编辑
- 弹窗提交
- 批量操作
- loading / 提示 / 空态 / 错误反馈

## 二、当前交互体系中的主要优点

### 1. 列表页操作入口已经较统一

大量列表页已经通过 `SearchTable` 接管：

- 搜索
- 重置
- 分页
- 工具栏
- 导出按钮扩展
- 刷新

这为后续统一列表交互节奏提供了很好的基础。

### 2. 搜索按钮和重置按钮已有统一组件层

`ActionButton.vue` 已经把：

- 查询
- 重置
- 展开/收起
- loading 态

做了基础统一。

说明搜索区交互不是散写的，后续只需要继续补规则，而不是重建。

### 3. 弹窗外壳已有统一能力

`Dialog.vue` 当前已提供：

- 统一头部
- 全屏切换
- 统一滚动容器
- 不允许点击遮罩关闭
- 统一 footer slot

这使得后续弹窗交互规范化是有落点的。

### 4. 高复杂度页面已经暴露出真实交互问题

例如：

- 代理列表中的行内编辑、批量修改、弹窗操作
- 能量订单中的停止代理、轮询刷新、详情弹窗

这些页面已经非常适合拿来抽交互规则，因为它们覆盖了多数典型问题。

## 三、当前存在的核心问题

## 3.1 成功后的默认动作仍过于依赖整表刷新

当前大量页面在操作成功后会直接：

- `searchTableRef.value?.reload()`

这虽然简单可靠，但也带来了明显的问题：

- 刷新会打断当前浏览节奏
- 大列表或慢接口场景体验不够顺
- 用户不一定知道是哪一行发生了变化
- 局部更新可解决的问题也被升级成整表刷新

这属于当前交互体验中最典型的“能用但不够丝滑”的地方。

## 3.2 行内编辑交互没有统一规范

当前项目中已经存在：

- 双击进入编辑
- 失焦保存
- 下拉即保存
- 开关即保存

这些模式都在用，但并没有统一规定：

- 什么时候进入编辑态
- 什么时候自动保存
- 保存失败后是否回滚
- 取消编辑怎么处理
- 是否显示局部 loading

结果就是：

- 用户在不同页面中会感受到不同的交互节奏
- 开发时也容易按当前页面习惯各写一套

## 3.3 批量操作体验不够标准化

当前项目已经有批量操作能力，但缺少统一规范，例如：

- 如何进入批量模式
- 批量模式下哪些操作必须禁用
- 已选择数量如何呈现
- 提交前是否需要确认
- 提交后如何反馈结果
- 取消批量时是否提示会撤销临时状态

这使得批量操作虽然可用，但还不算稳定、标准的后台交互模型。

## 3.4 搜索与重置行为还缺少更强的一致性约束

当前搜索区已有统一组件，但在实际页面层面仍存在一些差异：

- 有的页面重置后立即加载
- 有的页面重置后还带特殊逻辑
- 有的页面导出使用当前搜索条件
- 有的页面还会额外拼参数

这说明搜索组件统一了“按钮”，但还没有完全统一“行为规则”。

## 3.5 导出交互仍偏结果导向，缺少过程约束

当前导出能力多数已经统一走 `exportTableData`，但从交互体验看仍存在问题：

- 导出中 loading 不总是明确
- 空数据导出提示不完全统一
- 导出完成后反馈样式不完全统一
- 导出失败有时会显得过重或过轻

导出是高频后台动作，后续应统一为标准体验。

## 3.6 弹窗提交交互风格还不够一致

当前弹窗页虽然很多都用了统一 `Dialog`，但提交交互仍有差异：

- 有的使用 footer 中确定/取消
- 有的用 `onOk`
- 有的先校验再提交
- 有的缺少初始化失败反馈
- 有的 loading 只体现在按钮上
- 有的既弹全局错误又局部提示

这意味着：

- 弹窗外壳统一了
- 弹窗动作流没有完全统一

## 3.7 loading 与反馈层级还不够清晰

当前项目中 loading 常见形式包括：

- 页面容器 loading
- 表格 loading
- 弹窗提交按钮 loading
- 某些地方的全局 `ElLoading.service`

问题在于：

- 不同页面使用层级不同
- 用户不一定能快速判断当前是“列表加载中”还是“提交中”还是“轮询中”
- 某些操作缺少局部 loading，只能依赖成功/失败 toast

## 3.8 提示信息存在“数量多但语义层级不稳定”的问题

当前大量使用：

- `ElMessage.success`
- `ElMessage.warning`
- `ElMessage.error`
- `handleSuccessMessage`
- `handleErrorMessage`

但不同页面的使用策略不完全一致。

比如：

- 有些空列表会 info
- 有些失败会 error + 默认提示
- 有些用户主动取消也会出现 info
- 有些局部校验提示与全局失败提示混在一起

这说明消息提示已经很多，但“什么时候该提示、提示到什么层级” هنوز需要规则化。

## 四、后续统一规则

## 4.1 搜索与重置规则

### 规则一：搜索行为统一为“条件确认后刷新结果”

后续列表页搜索统一要求：

- 点击查询后刷新结果
- 分页自动回到第一页
- 搜索条件应作为当前上下文保留

页面不应重复定义自己的基础搜索行为，除非存在业务特殊性。

### 规则二：重置行为统一为“恢复默认条件 + 刷新结果”

后续重置统一要求：

- 恢复 schema 对应默认值
- 恢复默认分页
- 刷新结果

若某页面存在“重置后保留特定上下文”，必须显式说明并统一实现。

### 规则三：搜索按钮、重置按钮、展开按钮样式与位置保持一致

后续默认遵循：

- 查询按钮主按钮
- 重置按钮次按钮
- 展开/收起为文字型次操作

除页面特殊需要外，不随意改交互优先级。

---

## 4.2 列表刷新规则

### 规则一：优先局部更新，必要时整表刷新

后续统一策略：

- 行内状态切换、单字段更新优先局部更新
- 只有影响列表整体排序、筛选结果或统计信息时，才整表刷新

### 规则二：整表刷新必须保持用户上下文

若必须 `reload`，应尽量保持：

- 当前筛选条件
- 当前页码
- 当前排序
- 当前列表视角

避免刷新造成用户迷失。

### 规则三：轮询场景必须提供明确状态反馈

如订单轮询、异步状态变更场景，后续要求：

- 明确操作中态
- 明确轮询结束态
- 中间失败有清晰反馈

---

## 4.3 行内编辑规则

### 规则一：统一行内编辑模式

后续行内编辑建议统一支持以下模型之一：

- 显式进入编辑，显式保存
- 进入编辑后失焦保存
- 控件修改即提交

但同类交互在不同页面中尽量保持一致，不混用得过于随意。

### 规则二：行内编辑必须有失败回滚策略

后续要求：

- 更新失败后，UI 要么回滚
- 要么重新拉取该行数据
- 不允许让用户停留在一个“看起来改成功但其实失败”的状态

### 规则三：行内编辑必须有局部反馈

后续推荐：

- 当前单元格 loading
- 当前行禁用重复操作
- 成功后轻提示
- 失败后明确恢复

---

## 4.4 批量操作规则

### 规则一：批量模式必须有明确进入态和退出态

后续要求：

- 进入批量模式时有明显状态标识
- 非批量操作应按规则禁用
- 退出批量模式时清理临时选择和临时编辑值

### 规则二：批量操作必须展示选择结果

后续至少应明确：

- 已选择数量
- 当前待提交变更
- 未完成时不能误触其他冲突动作

### 规则三：批量提交要有结果摘要

后续建议：

- 至少提示成功数量
- 若存在失败，必要时补失败说明

---

## 4.5 导出规则

### 规则一：导出统一使用当前筛选上下文

后续所有列表导出默认基于当前搜索条件，而不是重新构造另一套与页面不一致的条件。

### 规则二：导出必须有过程状态

后续建议：

- 导出按钮支持 loading
- 导出中避免重复点击
- 空数据导出有统一提示

### 规则三：导出成功与失败提示语义统一

后续建议：

- 成功使用成功提示
- 空结果使用 info 或 warning
- 失败使用统一错误提示入口

---

## 4.6 弹窗提交规则

### 规则一：弹窗基础行为统一

基于当前 `Dialog`，后续统一保持：

- 关闭按钮位置统一
- 遮罩点击不关闭
- 默认 destroy-on-close
- footer 行为统一

### 规则二：弹窗提交统一遵循“校验 -> 提交 -> 反馈 -> 回流”

后续所有表单弹窗建议统一流程：

1. 校验表单
2. 设置按钮 loading
3. 执行提交
4. 成功提示
5. 关闭弹窗
6. 通知父级刷新或局部更新

### 规则三：弹窗初始化失败要明确可感知

例如详情弹窗、编辑弹窗、配置弹窗，若初始化失败：

- 要给出明确提示
- 要避免弹窗进入半残状态

---

## 4.7 loading 与反馈规则

### 规则一：loading 要按层级区分

后续统一按层级处理：

- 页面级：首次进入或全局切换
- 列表级：表格数据加载
- 行级：单条记录操作中
- 按钮级：提交/导出中
- 弹窗级：初始化或提交中

### 规则二：不同层级尽量不要混用

例如：

- 行内操作不要动不动触发整页 loading
- 导出不要使用全页 loading
- 列表刷新不要影响弹窗局部 loading

### 规则三：消息提示分级明确

后续统一建议：

- `success`：操作完成
- `warning`：用户输入或步骤不完整
- `info`：空结果、取消、提示性信息
- `error`：失败、异常

并且：

- 不对正常取消场景滥用 error
- 不对严重失败只给 info

## 七、当前阶段结论

当前项目的交互体系已经有一定统一基础，但更多统一在“组件存在”这一层，而不是“行为规则统一”这一层。

主要问题并不是缺按钮、缺弹窗、缺表格，而是：

- 高成功率场景过度依赖整表刷新
- 行内编辑没有统一模型
- 批量操作缺少标准行为
- 弹窗提交流程不够一致
- loading 与消息提示层级还不够清晰

因此这一块后续最合适的策略是：

- 先把高频交互规则写清
- 再选择几个高频页面做试点收口
- 最后逐步将规则下沉到公共组件和组合能力中

只要这一层规则建立起来，后续用户对系统的整体使用感会明显更稳定、更顺滑。
