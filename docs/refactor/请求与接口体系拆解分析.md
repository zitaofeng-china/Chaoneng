## 二、当前体系中的主要优点

### 1. 请求入口已经统一

当前项目没有让页面直接分散使用原生 `axios`，而是经过：

- `src/axios/index.ts`
- `src/axios/service.ts`

统一进入请求层。

这是非常重要的基础，因为只要入口统一，后面才有可能统一治理：

- token
- prefix
- 错误处理
- 取消请求
- 特殊请求配置

### 2. 双系统接口前缀已经在请求层处理

当前 `service.ts` 已根据 `VITE_SYSTEM_TYPE` 自动处理：

- `Management -> /v1`
- `Operation -> /v2`

这说明页面和 API 文件不需要重复感知系统差异，方向是正确的。

### 3. API 目录分层已经较完整

当前 `src/api` 已经按以下结构拆分：

- `common`
- `management`
- `opertion`

并进一步按业务模块归类。

这对后续治理很关键，因为接口归属已经有雏形，不需要再从“全部平铺接口”状态重新整理。

### 4. 列表参数、时间转换、导出已经有公共工具

`tableHelpers.ts` 已经封装了不少高频列表辅助能力，比如：

- 分页参数
- 时间区间转换
- 状态展示
- 导出

这说明项目已经意识到“页面重复流程需要抽出来”，只是目前还没有完全收口。

### 5. 错误消息提取已有基础 helper

`messageHelper.ts` 已具备：

- `getErrorMessage`
- `handleSuccessMessage`
- `handleErrorMessage`
- `handleWarningMessage`

后续只需要继续收敛使用方式，而不是从零设计消息体系。

## 三、当前存在的核心问题

## 3.1 请求层同时承担了“规则”和“业务兼容”

在 [service.ts](/abs/path/C:/Users/Administrator/Desktop/ChaoNeng/bot-frontend/src/axios/service.ts) 中，当前请求层除了处理通用能力，还额外承担了某些偏业务的逻辑，例如：

- 特定字段 `keyboards` 的数据清洗
- mock 分支判断
- prefix 拼接
- abort controller 维护

这说明请求层正在承接一部分本应更靠近业务或请求适配层的兼容逻辑。

问题在于：

- 请求层越往下越应该稳定
- 一旦把业务兼容直接塞进请求底座，后续维护成本会快速上升

## 3.2 参数转换职责还没有完全收口

当前参数转换分散在多个层：

- `service.ts` 里处理 URL、prefix、部分数据
- `config.ts` 里处理 GET 参数和表单数据
- `useSearchTable` 中处理分页字段和排序字段
- `tableHelpers.ts` 中处理时间范围和分页构造
- 页面里仍有大量手工拼装 API 参数

这会导致一个问题：

虽然项目里“有很多辅助函数”，但页面层仍然要自己知道很多转换细节。

## 3.3 错误提示存在多层重复处理风险

当前错误处理链大致是：

- `axios` 响应错误拦截器会提示“网络错误”
- `defaultResponseInterceptors` 会对非成功码提示业务错误
- 页面里又广泛使用 `handleErrorMessage`

这类结构容易带来两个问题：

- 某些错误提示重复弹出
- 某些错误该由哪层处理边界不明确

目前 `handleErrorMessage` 中已经尝试避免重复提示网络错误，但整体边界还不够彻底。

## 3.4 导出、列表辅助能力已有基础，但页面层重复仍然很多

虽然 `exportTableData` 已存在，但实际业务页面里仍然反复写：

- 构造导出参数
- try/catch
- 成功/失败提示
- 列表数据适配
- 排序或筛选条件二次拼装

这说明当前不是“缺工具”，而是“工具还不够接近页面实际使用模式”。

## 3.5 API 目录规范已形成，但命名与历史兼容仍然不统一

当前结构上的典型问题包括：

- `opertion` 目录拼写历史问题仍保留
- `type.ts` 与 `types.ts` 混用
- 同类 API 文件命名还不完全统一
- 个别模块已经迁移，个别模块仍带有旧时期命名风格

这些问题不一定影响运行，但会直接影响长期维护体验和规则一致性。

## 3.6 请求取消能力已存在，但调用规则未标准化

当前 `service.ts` 中已经支持：

- `cancelRequest`
- `cancelAllRequest`

但从整体使用方式看，还没有形成统一规则，例如：

- 列表切页时是否应该取消前一个请求
- 搜索条件快速切换时是否应该取消旧请求
- 弹窗初始化请求是否需要防重复
- 导出请求是否应该允许取消

能力已经有了，但没有制度化。

## 3.7 请求层配置项语义还不够稳定

例如：

- `skipErrorHandler`
- mock 列表控制
- response data 转换
- multipart/form-data 自动转换

这些功能都合理，但目前更像“逐步加上去的能力”，还缺少统一约束说明。

## 四、后续统一规则

## 4.1 请求入口规则

### 规则一：页面层不得绕开统一请求入口

后续所有请求都必须通过统一请求层发起。

允许形式：

- `request.get/post/put/delete`
- 基于统一封装的 API 方法

不建议：

- 页面直接新建 `axios` 实例
- 页面直接处理底层请求配置

### 规则二：请求底座只保留稳定通用能力

请求底座中应只保留：

- token 注入
- baseURL
- 版本前缀
- 统一序列化
- 统一取消
- 通用拦截器

不应继续增加：

- 特定业务字段清洗
- 特定业务模块兼容逻辑
- 单页面特殊处理

这类逻辑应向上移到 API 层或业务辅助层。

---

## 4.2 参数适配规则

### 规则一：系统级参数适配在请求层或 hook 层统一处理

后续需要继续统一的参数包括：

- `currentPage -> current_page`
- `pageSize -> page_size`
- 排序字段拼接
- GET 参数数组格式
- 时间范围转后端秒时间戳

原则：

- 通用转换不放页面层
- 页面层只处理业务专属参数差异

### 规则二：页面只描述业务含义，不描述协议细节

页面应该表达：

- 用户选了什么
- 业务要搜什么
- 业务要导出什么

而不应该过多表达：

- 后端字段如何命名
- 时间如何转秒
- 当前系统需要 `/v1` 还是 `/v2`

---

## 4.3 错误处理规则

### 规则一：错误处理必须分层

后续错误处理建议统一分三层：

1. 网络层错误
   - 连接失败
   - 超时
   - 中断
   - 由请求层统一处理

2. 协议层错误
   - 非成功码
   - token 失效
   - 由默认响应拦截器处理

3. 业务层错误
   - 某页面的业务失败提示
   - 由页面或业务 helper 处理

核心原则：

- 同一错误尽量只提示一次
- 哪层负责，就由哪层处理，不重复补提示

### 规则二：`handleErrorMessage` 只负责业务收口，不替代底层错误判断

后续建议：

- `handleErrorMessage` 继续作为页面层统一提示工具
- 但其职责应更清晰，只处理业务语义上的失败说明
- 不要让它承担底层请求层全部职责

### 规则三：可静默错误必须可配置

后续对于以下场景，应允许静默或局部处理：

- 取消请求
- 用户主动关闭弹窗后中断加载
- 轮询中间失败可重试
- 不希望弹全局错误的辅助查询

---

## 4.4 API 目录规则

### 规则一：继续按系统边界与页面结构归档

当前 API 目录方向是正确的，后续继续保持：

- `common` 只放真正跨系统或基础接口
- `management` 只放代理端接口
- `opertion` 只放运营端接口

### 规则二：模块目录应与页面模块保持一致

后续接口目录应尽量与页面模块结构保持同构，便于定位：

- 页面在哪个模块
- API 就优先放对应模块

### 规则三：命名规范逐步统一

后续建议逐步统一：

- `types.ts` 替代零散 `type.ts`
- 目录名与页面名保持稳定映射
- 旧命名只在兼容期保留

### 规则四：历史兼容目录不继续扩散

像 `opertion` 这类历史拼写问题，在未准备全量迁移前可以先保留，但后续不能继续把这种历史命名扩散到新的规则说明中。

可以保留兼容，但文档层与新规则层应明确标注：

- 这是历史兼容
- 不是新命名规范

---

## 4.5 导出与列表辅助规则

### 规则一：导出应统一走公共流程

后续导出动作建议统一包含：

- 获取当前筛选参数
- 构造导出参数
- 校验返回结构
- 数据映射
- 导出成功提示

页面不应每次重写整段流程。

### 规则二：列表辅助能力优先沉淀在统一 helper 或 composable

像这些能力应继续收口：

- 状态标签渲染
- 分页参数构造
- 搜索条件读取
- 日期范围转换
- 导出适配

原则是：

- 页面写业务差异
- helper 写公共流程

---

## 4.6 请求取消与并发控制规则

### 规则一：高频切换请求必须考虑取消旧请求

后续优先标准化这些场景：

- 列表快速切页
- 搜索条件连续修改后重新查询
- 弹窗频繁打开关闭
- 依赖输入关键字的远程查询

### 规则二：提交类动作必须考虑防重复提交

后续规范：

- 保存
- 提交
- 批量执行
- 导出

这些动作应统一考虑 loading 和防重复触发。

### 规则三：中断请求不应默认按业务失败提示

取消请求本身不是错误。

后续应明确：

- 取消请求不弹普通错误提示
- 中断请求不污染用户体验

## 七、当前阶段结论

当前项目的请求与接口体系已经具备不错的底座能力，但仍处于“有体系、未完全规范化”的状态。

它的主要问题不是基础太弱，而是：

- 底座中夹杂部分业务兼容
- 参数适配还没完全收口
- 错误处理边界不够彻底
- 页面层仍承担了不少重复流程
- API 命名与历史兼容尚未完全统一

因此这一块后续最合适的改造方式不是重写请求层，而是：

- 先明确职责边界
- 再收口重复适配与重复提示
- 最后逐步规范 API 结构与取消策略

只要这部分规则定清楚，后续列表体系、弹窗体系、统计页体系都会轻很多。
