# 状态管理与登录态拆解分析

## 文档目的

本文档用于分析 `bot-frontend` 当前的状态管理体系与登录态管理体系，并为后续修改建立统一规则与方向。

本文档重点关注：

- Pinia store 的职责边界
- 全局状态与页面状态的划分
- 持久化策略
- token 生命周期
- 登录、退出、过期处理
- 本地缓存与 store 的一致性问题

## 二、当前体系中的主要优点

### 1. store 基本按领域拆分，结构清楚

当前 store 模块不是大一统写法，而是按照领域拆分的：

- 用户
- 权限
- 应用
- 标签页
- 锁屏
- 语言

这对后续治理很有利，因为不需要先做“store 拆分”这一类高风险改造。

### 2. 用户态与权限态已经分离

当前并没有把：

- token
- userInfo
- route 权限结果

混在一个 store 里，而是分别由：

- `user`
- `permission`

承接。

这意味着登录态和路由态已经具备继续收口的基础。

### 3. 标签页缓存状态独立维护

`tagsView` store 当前单独维护：

- visitedViews
- cachedViews
- selectedTag

这是一种比较合理的做法，因为标签系统本身就是一个相对独立的领域。

### 4. 应用级 UI 状态有集中管理基础

`app` store 当前承载：

- 布局
- 主题
- 尺寸
- breadcrumb
- tagsView
- dynamicRouter
- serverDynamicRouter

这些状态虽然稍多，但至少都集中在同一个 UI 层级状态容器里，而不是页面散写。

### 5. 登录态退出流程已有统一入口

当前 `userStore.reset()` 已负责：

- 清空用户信息
- 清空 token
- 清除 tags
- 重置权限状态
- 清理部分 localStorage
- 跳转登录页

说明退出流程已经有一个主入口，而不是完全散落各处。

## 三、当前存在的核心问题

## 3.1 store 边界基本存在，但状态归属还不够彻底

当前仍存在一些边界模糊情况，例如：

- `dynamicRouter`、`serverDynamicRouter` 在 `app` store 中
- 但其实际影响的是权限生成与路由行为
- `user` store 中保存 `roleRouters`
- `permission` store 中又负责生成实际路由

这意味着部分状态归属虽然可用，但语义上并不完全干净。

问题不一定马上爆发，但后续继续扩展会更难判断：

- 某个状态到底属于 UI、权限还是用户态

## 3.2 持久化策略过宽，且缺少统一原则

当前状态中存在：

- `app`：`persist: true`
- `user`：`persist: true`
- `lock`：`persist: true`
- `permission`：部分持久化
- `tagsView`：不持久化

问题不是“用了持久化”，而是“哪些该持久化、哪些不该持久化，还没有统一规则”。

潜在风险包括：

- 旧状态污染新会话
- 临时 UI 偏好与关键业务状态混存在一起
- 路由模式等状态跨刷新残留
- 调试和线上问题排查更困难

## 3.3 本地存储与 store 双源读取导致一致性风险

当前典型问题体现在：

- `permission.ts` 中直接读取 `localStorage.user`
- `utils/is.ts` 中直接读取 `localStorage.user`
- 某些逻辑依赖 store
- 某些逻辑依赖 localStorage 原始值

这意味着当前系统存在“双数据源”：

1. store 内部状态
2. localStorage 原始缓存

一旦两者不一致，就会出现：

- 逻辑判断不统一
- 调试困难
- 某些页面表现与守卫判断不同步

## 3.4 token 生命周期规则还没有完全模块化

当前 token 相关逻辑分散在：

- `user` store
- 路由守卫
- 请求拦截器
- 登录页初始化逻辑

特别是 token 过期判断：

- 一部分逻辑在守卫里
- 一部分登出逻辑在 `userStore`
- 一部分失效码处理在 `axios/config.ts`

这说明“token 生命周期存在”，但还没有形成统一会话模型。

## 3.5 `reset/logout` 流程能力够用，但耦合较重

当前 `userStore.reset()` 除了处理用户态，还会：

- 清 tagsView
- 清 permission 状态
- 清 localStorage 指定 key
- 路由跳转

这种做法短期很方便，但长期问题是：

- 用户域 store 承担了过多跨领域清理职责
- 退出流程和状态清理耦合偏深
- 后面若想支持更多退出策略或局部清理，会不够灵活

## 3.6 `app` store 承载内容偏多

`app` store 当前已经涵盖：

- 主题
- 布局
- 设备状态
- 页脚
- 菜单折叠
- tagsView 开关
- breadcrumb
- dynamicRouter
- serverDynamicRouter

这说明 `app` store 已经接近“应用总配置大仓库”。

问题在于：

- UI 状态和系统运行模式状态混在一起
- 后续继续往里塞，会进一步变重

## 3.7 页面状态与全局状态边界还需要更强约束

虽然当前并没有明显把大量页面状态都塞进 store，但从整体结构和使用方式看，仍然需要明确：

- 页面内搜索条件
- 弹窗显示状态
- 列表局部编辑态
- 页面级 temporary selection

这些都不应进入全局 store。

这部分现在更多靠惯例，而不是强规则。

## 四、后续统一规则

## 4.1 store 领域边界规则

### 规则一：store 只承载真正跨页面、跨会话、跨模块的状态

适合进入 store 的内容：

- 用户信息
- token
- 权限结果
- 应用主题
- 布局偏好
- 标签页
- 语言设置

不适合进入 store 的内容：

- 页面筛选条件
- 页面弹窗显示状态
- 页面临时表单值
- 单页局部 loading
- 行级编辑状态

### 规则二：UI 状态与系统运行模式状态要逐步分层

后续建议逐步明确：

- `app` store 主要承载 UI/布局偏好
- 路由模式、动态路由模式等更偏系统行为的状态，应避免继续无限堆入 `app`

即使短期不拆 store，也要在规则上明确其语义边界。

### 规则三：用户域状态与权限域状态继续分离

后续继续保持：

- `user` 负责身份、token、userInfo
- `permission` 负责权限结果和路由生成结果

同时减少交叉写入和职责重叠。

---

## 4.2 持久化规则

### 规则一：默认不持久化，只有明确有价值的状态才持久化

后续持久化策略应遵循：

- 能不持久化就不持久化
- 只有跨刷新仍然有业务价值或体验价值的状态才持久化

### 规则二：关键身份状态持久化要谨慎

像以下状态若持久化，必须明确理由与清理策略：

- token
- tokenExpiredAt
- userInfo
- roleRouters

要特别考虑：

- 是否存在旧状态残留
- 是否和后端会话失效不同步
- 是否需要启动时再校验

### 规则三：持久化字段必须可审计

后续要求：

- 每个 store 的持久化字段应明确列出用途
- 不建议继续使用“整个 store 全持久化”作为默认方案

优先使用：

- `pick`
- 更细粒度字段持久化

---

## 4.3 登录态与 token 生命周期规则

### 规则一：登录态判断必须单源

后续应逐步收口为：

- 优先以 store 为主状态源
- localStorage 只作为持久化底层，不作为业务层直接读取源

这意味着：

- 页面和工具函数不应继续直接解析 `localStorage.user`
- token 是否有效、用户是否登录，应通过统一方法判断

### 规则二：token 生命周期应统一由会话规则控制

后续应统一表达：

- token 什么时候算有效
- token 什么时候算失效
- 失效后由谁负责触发退出
- 退出时由谁负责清理哪些状态

避免：

- 守卫判一套
- 请求拦截器判一套
- 页面判一套

### 规则三：登出流程应分成“状态清理”和“跳转处理”

后续建议将退出拆成两个层面：

1. 清理用户会话
2. 跳转到登录页

这样可以减少 `userStore.reset()` 对其他系统模块的硬耦合。

---

## 4.4 本地缓存规则

### 规则一：localStorage 只作为存储介质，不作为业务判断入口

后续规则：

- 除初始化恢复、底层持久化外，业务层不应直接读 localStorage
- 所有业务判断优先通过 store getter 或统一 helper 完成

### 规则二：缓存清理策略必须集中管理

退出登录、切换身份、token 失效时，缓存清理必须由统一流程控制。

不建议：

- 各页面自己清某几个 key
- 各模块自己随意处理 localStorage

### 规则三：缓存 key 清单应明确

后续建议建立统一缓存清单说明，例如：

- 哪些 key 属于 app
- 哪些属于 user
- 哪些属于 permission
- 哪些在 logout 时必须清空

避免未来继续扩展后没人能完整掌握缓存体系。

---

## 4.5 标签页与缓存视图规则

### 规则一：标签页状态只服务导航体验，不承接业务态

`tagsView` 应继续只承接：

- 标签记录
- 缓存页记录
- 当前选中标签

不应承接页面业务数据。

### 规则二：缓存视图生成规则应与路由 meta 保持统一

后续继续以：

- `meta.noTagsView`
- `meta.noCache`
- `meta.affix`

作为标签/缓存行为主依据，避免页面额外分散控制。

## 五、建议处理的小点

## 5.1 `user` store 侧

- 收口 token 生命周期逻辑
- 减轻 `reset/logout` 的跨领域耦合
- 明确用户态字段哪些应持久化
- 统一登录态判断来源

## 5.2 `permission` store 侧

- 继续保持权限态独立
- 减少与用户态、路由态的隐式耦合
- 重新审视持久化必要性

## 5.3 `app` store 侧

- 梳理哪些是 UI 偏好
- 梳理哪些是系统模式
- 避免继续无限扩容
- 必要时为未来拆分预留边界

## 5.4 本地缓存侧

- 清理直接读取 `localStorage.user` 的逻辑
- 收口退出时缓存清理规则
- 补统一缓存 key 说明

## 5.5 登录退出流程侧

- 统一 token 失效触发路径
- 统一手动退出路径
- 统一登录后初始化状态恢复路径

## 六、建议推进顺序

### 第一阶段：先定状态边界与持久化规则

优先完成：

- 哪些状态属于 store
- 哪些状态应该持久化
- localStorage 是否允许直接业务读取

### 第二阶段：收口登录态与退出流程

优先处理：

- token 生命周期规则
- logout/reset 流程拆分
- 缓存清理统一

### 第三阶段：细化 store 语义边界

优先处理：

- `app` store 负担整理
- `permission` 与 `user` 的依赖关系收口
- 页面状态不入全局的规则落地

---

## 七、当前阶段结论

当前项目的状态管理体系基础是存在的，而且总体方向是正确的：

- store 已按领域拆开
- 用户态与权限态已分离
- 标签页和布局态也有独立模块

真正的问题不在于“没有 store 体系”，而在于：

- 持久化边界不够严格
- 本地缓存与 store 双源并存
- token 生命周期规则还没完全统一
- logout/reset 流程耦合偏重
- `app` store 承载内容有继续膨胀风险

因此这一块后续最合适的策略不是重写 store，而是：

- 先定状态边界
- 再定持久化规则
- 再统一登录态生命周期
- 最后逐步优化 store 内部职责

只要这部分规则立稳，权限体系、请求体系、页面体系的稳定性都会一起提升。
