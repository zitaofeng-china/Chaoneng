# 公共组件与页面逻辑优化三大方向分析

## 文档目的

本文档用于沉淀当前 `bot-frontend` 项目在公共组件、页面逻辑、列表交互上的优化方向。重点不是追求短期内快速改完，而是以“稳重推进、完成度优先、影响面可控”为原则，先形成统一认知，再逐步落地。

当前分析重点围绕以下三大方向展开：

1. 重复能力的去重与组合
2. 非必要逻辑反复调用的去除
3. 交互体验中不够合理部分的优化

本文档不直接定义具体开发排期，但会明确每个方向下建议优先处理的小点，方便后续分阶段实施。

---

## 一、重复能力的去重与组合

### 方向目标

当前项目已经具备比较完整的公共组件体系，尤其是列表页相关的 `SearchTable`、`Search`、`Form`、`Table`、`useSearchTable`、`useTable` 等能力，复用程度较高。但随着业务扩展，部分能力开始出现职责重叠、边界不清、同类逻辑分散维护的问题。

这一方向的核心目标不是“继续加抽象”，而是把已经重复的能力重新收口，形成更清晰、更稳定的分层关系。

### 需要处理的小点

#### 1. 明确 `Table` 与 `SearchTable` 的职责边界

当前现状：

- `Table` 除了负责表格展示，还承担了部分容器级行为。
- `SearchTable` 除了负责搜索 + 数据编排，也在承担一些表格容器行为。
- 两者在一些能力上存在交叉，比如滚轮横向滚动、列表容器控制、工具栏整合。

建议处理：

- 将 `Table` 收敛为“纯表格展示层”，只负责：
  - 列渲染
  - 特殊列类型
  - 分页展示
  - 行/列显示行为
- 将 `SearchTable` 收敛为“列表页编排层”，只负责：
  - 搜索区
  - 工具栏
  - 分页联动
  - 数据装载
  - 对外暴露 `reload/reset/search`
- 所有偏容器级行为，只保留一处归属，避免双层接管。

#### 2. 重新梳理 `useTable`、`useSearch`、`useSearchTable` 的主次关系

当前现状：

- `useTable` 负责请求触发、分页监听、删除逻辑、实例代理。
- `useSearchTable` 又在其基础上叠加搜索参数、排序转换、权限控制、初始化流程。
- `useSearch` 负责 Search 实例方法透传。

问题在于：

- 这三层都“有能力”，但没有形成足够清晰的主从结构。
- 后续新增能力时，容易出现“不确定应该加在哪一层”的情况。

建议处理：

- 将 `useTable` 收敛为“表格状态层”：
  - `loading`
  - `dataList`
  - `total`
  - `currentPage`
  - `pageSize`
- 将 `useSearch` 保持为“搜索表单实例代理层”。
- 将 `useSearchTable` 定义为唯一“列表页编排层”：
  - 参数合并
  - 排序处理
  - 搜索触发
  - 重置触发
  - 刷新触发
  - 权限接入

#### 3. 将高频列表页模式提炼为稳定的页面级组合能力

当前现状：

- 很多业务页面虽然业务不同，但骨架高度相似。
- 普遍都在做：
  - 搜索 schema 定义
  - 列定义
  - 获取列表
  - 导出
  - 操作成功后刷新
  - 异常提示

建议处理：

- 抽象统一的列表页组合能力，例如：
  - `useCrudListPage`
  - `useTableActions`
  - `useTableExport`
- 目标不是完全屏蔽业务差异，而是减少页面层重复模板代码。

#### 4. 将表格内编辑、状态切换、单字段更新类能力做统一模型

当前现状：

- 许多页面把 `ElSwitch`、`ElSelect`、`ElAutocomplete`、按钮操作等直接放在列表列里。
- 这种模式很高效，但实现方式分散。

建议处理：

- 统一抽离“表格内动作模型”：
  - 单字段即时更新
  - 保存中态
  - 成功提示
  - 失败回滚
  - 是否局部刷新/整表刷新
- 页面只保留业务本身，不再重复处理交互细节。

#### 5. 统一导出、提示、空数据提示等横切能力

当前现状：

- 项目里已经有 `exportTableData`、`handleSuccessMessage`、`handleErrorMessage` 等公共能力。
- 但很多页面还是在其外侧包了大量重复流程。

建议处理：

- 在不破坏现有功能的前提下，继续收敛常见横切逻辑：
  - 导出前校验
  - 导出参数构造
  - 成功/失败提示
  - 空结果提醒
- 避免页面重复写一整段类似流程。

### 本方向落地原则

- 不急于一口气重写整套列表体系。
- 优先先做边界收口，再做组合能力抽离。
- 每次收口都要保证老页面兼容，尽量避免大面积一次性改造。

## 二、非必要逻辑反复调用的去除

### 方向目标

项目当前的主要问题不是“没有复用”，而是“已经复用后，某些逻辑又在多个层级被重复触发”。这类问题会直接影响维护成本、页面稳定性和请求效率。

这一方向的核心目标，是将重复触发、重复刷新、重复监听、重复计算等问题系统性减掉，让调用关系更清晰。

### 需要处理的小点

#### 1. 去掉重复挂载的行为逻辑

当前现状：

- `SearchTable` 与 `Table` 都接入了横向滚轮滚动能力。

问题：

- 行为来源重复，后续定位问题困难。
- 存在重复绑定、重复维护的风险。

建议处理：

- 将该能力只保留在一层，推荐收口到 `Table`。
- `SearchTable` 不再额外接管相同的 DOM 行为。

#### 2. 减少不必要的整表 `reload`

当前现状：

- 项目中存在大量 `searchTableRef.value?.reload()`。
- 很多操作在成功后刷新整表。
- 某些失败场景也会再次刷新整表。

问题：

- 页面会出现不必要的重复请求。
- 轻量操作也会打断用户当前浏览节奏。
- 对复杂筛选、慢接口场景体验不够友好。

建议处理：

- 建立统一刷新策略：
  - 哪些操作必须整表刷新
  - 哪些操作只需局部更新当前行
  - 哪些操作只需更新局部状态
- 将“刷新”从默认动作改为按场景决策。

#### 3. 收敛 `watch` 驱动请求与手动请求的双重触发问题

当前现状：

- `useTable` 中通过监听 `currentPage`、`pageSize` 触发请求。
- 页面和上层 hook 中又会主动调用 `getList/reload`。

问题：

- 某些状态变更可能引发重复请求。
- 请求来源不够单一，后期排查困难。

建议处理：

- 统一请求入口。
- 明确“状态变更”和“数据加载”谁负责驱动谁。
- 尽量减少既有 `watch` 自动触发、又有外部手动触发的双轨模式。

#### 4. 清理页面中的重复数据转换逻辑

当前现状：

- 很多列表页都在手动做：
  - 参数适配
  - 排序适配
  - 分页字段适配
  - 时间区间转换
  - 导出字段转换

问题：

- 这些逻辑是合理的，但散落在页面里重复书写。
- 长期会让页面逻辑变重。

建议处理：

- 统一沉淀数据转换工具或组合式方法。
- 页面只保留业务差异化转换，不再重复写基础通用转换。

#### 5. 清理页面中的重复提示与异常分支

当前现状：

- 大量页面存在相似的 try/catch + 提示 + reload 模式。
- 同类错误处理实现方式不完全一致。

建议处理：

- 抽统一的执行器方法，例如：
  - 动作执行
  - 成功提示
  - 失败提示
  - 是否刷新
- 减少每个页面手写重复异常分支。

#### 6. 减少列表页运行时动态改列的无序使用

当前现状：

- `Table` 暴露了 `setColumn`、`addColumn`、`delColumn` 等能力，灵活性较高。
- 如果页面没有统一规范，容易在不同地方动态修改列配置。

问题：

- 会提高状态变化复杂度。
- 不利于后续问题排查和复用。

建议处理：

- 给动态列修改定义使用场景边界：
  - 哪些场景允许运行时改列
  - 哪些场景应优先通过 computed columns 解决
- 控制运行时列修改的入口数量。

### 本方向落地原则

- 优先去掉“明显重复调用”的部分。
- 不追求先做极致性能优化，而是先把调用关系理顺。
- 每减少一次非必要调用，都是在给后续重构降风险。

## 三、交互体验中不够合理部分的优化

### 方向目标

当前项目整体功能已经比较完整，但后台系统的交互体验还有进一步优化空间。这里说的“交互优化”不只是视觉层面的好看，而是用户在搜索、编辑、批量操作、列设置、刷新反馈时是否顺手、是否稳定、是否容易理解。

这一方向的核心目标，是提升后台系统使用过程中的流畅度和确定性。

### 需要处理的小点

#### 1. 优化表格内直接编辑的交互一致性

当前现状：

- 表格中已经大量使用直接编辑模式。
- 比如开关、下拉、邮箱输入、按钮操作等。

问题：

- 不同页面的保存反馈方式不完全一致。
- 失败后的回滚行为不统一。
- 编辑态和浏览态切换规则不统一。

建议处理：

- 建立统一的表格内编辑交互规范：
  - 点击/双击进入编辑
  - 失焦是否保存
  - 回车是否保存
  - 保存中是否禁用
  - 失败后是否恢复原值
  - 是否给出明确状态反馈

#### 2. 优化列表操作后的反馈机制

当前现状：

- 当前项目大多数操作后会 toast 提示，再整表刷新。

问题：

- 用户能知道“成功了”，但不一定能清晰感知“哪里变化了”。
- 长表格场景中刷新会打断阅读和操作节奏。

建议处理：

- 优先引入行级反馈：
  - 当前操作按钮 loading
  - 当前行局部更新
  - 必要时才整表刷新
- 对批量操作补充更明确的结果反馈：
  - 成功条数
  - 失败条数
  - 可选失败明细

#### 3. 优化搜索区域的使用体验

当前现状：

- `Search` 能力比较强，功能完整。
- 但在部分业务页里，搜索项较多，认知负担偏高。

建议处理：

- 区分主筛选项和高级筛选项。
- 默认只展示高频字段，低频字段折叠。
- 对重置策略做统一定义，避免“重置后与用户预期不一致”。
- 优化字段排序规则，不只按组件类型，也考虑业务优先级。

#### 4. 优化列表工具栏与列设置交互

当前现状：

- `TableActions` + `ColumnSetting` 已经具备刷新、尺寸调整、列显隐、固定、拖拽排序能力。

问题：

- 交互已经可用，但仍偏“功能堆叠”。
- 缺少状态持久化与搜索辅助。

建议处理：

- 为列设置增加本地持久化能力。
- 增加列名搜索。
- 适当拆分“显示控制”和“固定控制”的认知区块。
- 让还原行为更明确，避免用户不清楚会恢复到哪个状态。

#### 5. 优化大列表、慢接口场景的加载感知

当前现状：

- 当前大多数列表通过全局 loading 提示加载。

问题：

- 用户知道“在加载”，但不清楚是首次加载、筛选刷新还是局部操作中。

建议处理：

- 区分不同加载态：
  - 首次加载
  - 搜索中
  - 重置中
  - 行级操作中
  - 导出中
- 让用户感知更准确，减少误判。

#### 6. 优化批量操作的可理解性和安全感

当前现状：

- 部分页面已有批量操作模式，但流程说明较弱。

问题：

- 用户可能不知道当前是否处于“批量编辑模式”。
- 对已选择对象、待提交变更、取消后影响范围的理解不够直观。

建议处理：

- 明确显示批量模式状态。
- 提示当前已选择数量。
- 在提交前给出简要确认信息。
- 取消时明确告诉用户会撤销哪些临时改动。

### 本方向落地原则

- 优先优化会影响日常高频操作的交互。
- 不急于一次性大改视觉层，而是先把行为一致性做好。
- 所有交互优化都应建立在现有业务稳定的前提下推进。

## 四、整体推进建议

### 建议推进方式

为了兼顾稳定性与完成度，建议采用“先收口、再抽象、后优化体验”的顺序，而不是直接大面积改造。

### 建议分阶段处理

#### 第一阶段：统一认知与边界收口

目标：

- 明确 `Table`、`SearchTable`、`useTable`、`useSearchTable` 的职责
- 去掉明显重复能力
- 确认哪些能力保留，哪些能力下沉/上收

建议先处理：

- 横向滚轮逻辑归属
- 列表请求触发入口梳理
- reload 策略初步分类

#### 第二阶段：沉淀稳定组合能力

目标：

- 把页面上高度重复的逻辑抽到组合式能力里

建议先处理：

- 列表页通用请求模型
- 导出模型
- 动作执行模型
- 行内编辑模型

#### 第三阶段：分模块优化交互

目标：

- 在不破坏业务的前提下，提升使用流畅度

建议先处理：

- 表格内编辑统一体验
- 列设置与工具栏体验
- 批量操作反馈
- 大列表加载态区分

## 五、当前结论

从当前项目状态来看，最需要的不是继续快速叠加功能，而是对已有公共组件体系做一次稳妥治理。

三大方向可以统一理解为：

- 第一方向解决“能力重复、边界重叠”的问题
- 第二方向解决“逻辑调用分散、重复触发”的问题
- 第三方向解决“用户操作过程不够顺手、不够一致”的问题

后续所有改动建议遵循以下原则：

- 稳定优先于速度
- 完成度优先于表面上的大改动
- 小步收口优先于一次性重构
- 先解决高频问题，再处理长尾优化

如果后续进入实际改造阶段，建议以本文件为基准，继续补充每一项对应的目标文件、改造顺序、影响范围和验收标准。
