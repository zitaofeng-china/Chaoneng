# 重构实施批次计划

## 文档目的

本文档用于将当前已经完成的分析与规则文档，进一步收束为可执行的实施批次计划。

本文档不直接替代专题分析文档，而是负责回答以下问题：

- 先改什么
- 后改什么
- 哪些可以并行
- 哪些必须前置
- 每一批的目标是什么
- 每一批改完后如何判断可以进入下一批

本文档适用于“稳妥推进、完成度优先”的重构方式，不适用于一次性大面积并发重写。

---

## 一、实施总原则

### 1. 先规则落地，再代码重构

当前项目已经完成的主要工作是：

- 规则统一
- 专题拆解
- 主要修改方向确认

因此后续实施不能再回到“看到哪里不顺手就改哪里”的方式，而应当严格遵循：

- 先明确本批目标
- 再识别本批影响范围
- 最后集中改一类问题

### 2. 每一批只解决一个主问题

后续批次应尽量聚焦，不建议一批内同时大改：

- 列表体系
- 路由体系
- 请求体系
- 状态体系

否则风险会被放大，验证成本也会显著上升。

### 3. 优先高收益、低耦合、可验证项

优先顺序建议为：

1. 去重与规则收口
2. 重复调用与基础交互优化
3. 结构边界调整
4. 命名、清理、迁移类工作

### 4. 每一批必须可回退、可验收

每一批开始前都应明确：

- 改哪些文件
- 不改哪些文件
- 主要风险是什么
- 如何验证
- 出问题时如何回退

## 三、建议实施批次总览

建议整体分为 6 个批次推进：

1. 第一批：公共列表体系收口
2. 第二批：请求与提示流程收口
3. 第三批：交互一致性试点落地
4. 第四批：路由与权限规则收口
5. 第五批：状态管理与登录态收口
6. 第六批：页面结构迁移与历史清理

这 6 个批次并不是所有工作完全线性，但建议以此作为主顺序。

## 四、分批次实施方案

## 第一批：公共列表体系收口

### 目标

优先解决当前项目中最高频、最容易重复、影响面最大的部分：

- `Table`
- `SearchTable`
- `Search`
- `Form`
- `useTable`
- `useSearchTable`

### 本批重点

- 去除明显重复能力
- 梳理组件职责边界
- 梳理 hook 编排边界
- 统一列表基础模型

### 主要处理方向

- 收口 `Table` 与 `SearchTable` 的职责
- 去掉重复横向滚动逻辑
- 梳理 `useTable` 与 `useSearchTable` 的请求编排关系
- 统一列表的 `reload/reset/search` 基础语义

### 优先级

最高优先级。

原因：

- 使用频率最高
- 后续很多批次都依赖这里的稳定性
- 能最快带来去重收益

### 本批适合改动的文件范围

- `src/components/Table`
- `src/components/SearchTable`
- `src/components/Search`
- `src/components/Form`
- `src/hooks/web/useTable.ts`
- `src/hooks/web/useSearchTable.ts`
- 必要时少量配套 helper

### 本批不建议触碰

- 路由守卫主逻辑
- 登录态主逻辑
- 页面目录迁移
- 大面积业务页面调整

### 本批完成标志

- 列表主链职责清晰
- 组件间重复行为减少
- 列表型页面可以在不改变业务行为的前提下继续复用

---

## 第二批：请求与提示流程收口

### 目标

在列表主链稳定后，统一请求层和页面层之间的调用与反馈方式。

### 本批重点

- 参数适配收口
- 错误处理分层收口
- 导出流程收口
- 减少页面层重复提示逻辑

### 主要处理方向

- 清理请求底座中的业务兼容逻辑
- 统一页面层错误提示入口
- 统一导出模型
- 减少页面层重复参数转换

### 优先级

高优先级。

原因：

- 与第一批耦合较强
- 会直接影响后续高频页面试点体验

### 本批适合改动的文件范围

- `src/axios`
- `src/utils/messageHelper.ts`
- `src/utils/tableHelpers.ts`
- 部分高频 API 文件
- 少量高频列表页

### 本批不建议触碰

- 权限主逻辑
- 页面目录大迁移
- store 大调整

### 本批完成标志

- 页面层错误提示不再多头处理
- 导出流程统一
- 常见参数转换有统一入口

---

## 第三批：交互一致性试点落地

### 目标

选取高频页面，将规则层定义的交互规范落地为真实可感知的体验改进。

### 本批重点

- 搜索/重置一致性
- 行内编辑一致性
- 批量操作一致性
- 弹窗提交一致性
- loading 分层

### 主要处理方向

- 优先选择 2 到 4 个高频页面做试点
- 验证“局部刷新优先于整表刷新”的策略
- 统一弹窗提交流程
- 统一批量模式行为

### 建议试点页面

- `operation/Agent/AgentList`
- `operation/OperationCenter/EnergyTransaction`
- 一个代理端高频列表页
- 一个高频弹窗场景页

### 优先级

高优先级，但应在第一、二批之后进行。

### 本批适合改动的文件范围

- 少量高频业务页面
- 与这些页面直接相关的业务弹窗
- 必要的公共按钮/弹窗/列表辅助逻辑

### 本批完成标志

- 至少完成一组可复制的交互标准样板
- 后续页面可按样板持续收敛

---

## 第四批：路由与权限规则收口

### 目标

在页面主链和基础交互稳定后，开始整理系统底层访问控制结构。

### 本批重点

- 路由规则边界清晰化
- 权限判断收口
- 按钮权限规则统一
- meta 约定补齐

### 主要处理方向

- 收口系统差异判断位置
- 收口权限判断工具
- 补齐路由 meta 类型约束
- 清理黑名单与临时过滤逻辑

### 优先级

中高优先级。

原因：

- 重要，但改动风险大于前三批
- 需要建立在前面主链稳定的基础上推进

### 本批适合改动的文件范围

- `src/router`
- `src/permission.ts`
- `src/store/modules/permission.ts`
- `types/router.d.ts`
- 权限辅助工具与指令

### 本批完成标志

- 权限判断路径更单一
- 路由生成规则更清晰
- 页面和按钮权限逻辑更可解释

---

## 第五批：状态管理与登录态收口

### 目标

统一身份状态、缓存策略、退出流程和 token 生命周期。

### 本批重点

- 持久化策略收口
- localStorage 直读清理
- token 生命周期统一
- logout/reset 流程收口

### 主要处理方向

- 审视各 store 的持久化范围
- 收口 store 与 localStorage 双源问题
- 统一登录态判断入口
- 梳理退出流程清理边界

### 优先级

中优先级。

原因：

- 很重要
- 但涉及全局行为，需放在前面几批稳定后进行

### 本批适合改动的文件范围

- `src/store/modules/*`
- `src/permission.ts`
- `src/axios/config.ts`
- 直接读取 `localStorage.user` 的工具文件

### 本批完成标志

- 登录态判断单源化
- 持久化策略更可控
- 登出清理流程更稳定

---

## 第六批：页面结构迁移与历史清理

### 目标

在核心规则和高频链路稳定后，再推动历史结构迁移和清理。

### 本批重点

- `views` 职责收口
- 历史页面迁移
- API 同构迁移
- 无用目录与旧引用清理

### 主要处理方向

- 逐步把仍需迁移的真实业务页迁入 `operation/management`
- 清理旧页面引用
- 清理历史 API 引用
- 保留演示页和基础页的合理边界

### 优先级

中优先级，偏后置。

原因：

- 结构清理重要，但不应先于高频主链收口
- 太早做容易和前面几批互相打架

### 本批适合改动的文件范围

- `src/views`
- `src/operation`
- `src/management`
- `src/api`
- 对应路由导入

### 本批完成标志

- 页面结构边界更清晰
- 历史目录负担减轻
- 路由、页面、API 同构关系更稳定

---

## 五、批次之间的依赖关系

### 强依赖关系

- 第二批依赖第一批
- 第三批依赖第一批和第二批
- 第四批可与第三批部分并行，但建议在第一、二批稳定后开始
- 第五批建议在第四批前后推进，但不建议早于第二批
- 第六批建议放在前五批核心规则落地之后

### 可并行的局部工作

可适度并行的内容包括：

- 文档补充
- 文件映射整理
- 页面盘点
- API 命名盘点
- 权限字段盘点

但核心代码改造不建议多批并发推进。

## 六、每一批的风险控制建议

## 第一批风险

- 公共组件改动影响大量页面

控制方式：

- 先保兼容接口
- 先不动页面业务行为
- 改完立即跑高频页面回归

## 第二批风险

- 错误提示与导出流程改动容易影响用户感知

控制方式：

- 保留旧提示路径兼容期
- 先从高频列表页试点

## 第三批风险

- 交互体验变化最容易引发“习惯迁移问题”

控制方式：

- 先做试点页
- 不大面积同时替换

## 第四批风险

- 路由权限改错会直接导致页面不可访问

控制方式：

- 权限变更必须有完整验证
- 先做类型与规则收口，再做行为收口

## 第五批风险

- 登录态与缓存改动影响全局

控制方式：

- 明确测试登录、退出、过期、刷新恢复全链路

## 第六批风险

- 迁移与清理可能导致路径断裂

控制方式：

- 严格按“迁移 -> 引用切换 -> 搜索确认 -> 清理”顺序执行

---

## 七、每一批完成后的最低验证要求

每一批完成后，至少应完成以下验证：

### 通用验证

- 类型检查通过
- 构建通过
- 关键页面能打开
- 无明显控制台报错

### 列表相关验证

- 搜索可用
- 重置可用
- 分页可用
- 排序可用
- 导出可用

### 权限相关验证

- 登录可进入
- 无权限页面表现正常
- 按钮权限表现正常

### 登录态相关验证

- 登录后刷新可恢复
- 退出后状态清空
- 过期后跳转正确

---

## 八、当前建议的第一落地批次

如果现在准备真正开始改代码，建议从第一批开始：

### 第一批起始目标

- 收口公共列表体系
- 不追求一次性解决所有问题
- 先把“重复能力”和“重复调用链”打掉一部分

### 第一批建议优先改造对象

- `SearchTable`
- `Table`
- `useSearchTable`
- `useTable`

### 第一批建议先做的具体动作

1. 去掉重复横向滚动逻辑
2. 梳理列表请求触发入口
3. 梳理 `reload/reset/search` 的标准语义
4. 收口组件职责边界

这会是后续所有批次最稳的起点。

---

## 九、当前阶段结论

当前项目已经具备进入实施阶段的条件，但不适合直接大范围开改。

最稳妥的路线是：

1. 以本文档确定改造批次
2. 先从第一批公共列表体系开始
3. 每一批做完后完成最低验证
4. 确认稳定后再进入下一批

也就是说，后续不再是“想到哪里改哪里”，而是进入“按批次推进”的系统治理阶段。
